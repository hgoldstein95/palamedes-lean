Making generator synthesis robust

A plan to retire most of the guarding and the per-combinator norm_for_* cascade in CGeneratorSearch.lean by hoisting convert to a single canonicalizing step — without the abandoned Desc/Canonical re-architecture, and without giving up what convert buys us.

convert is not the smell. It does two jobs at once, and only one of them hurts. As an adaptor — a value-transparent bridge that parks a propositional equality in a proof-erased field — it is exactly what keeps extraction clean and makes synthesis complete up to provable equality. As a router — the way apply convert ?pf ?arg defers rule choice to whichever norm_for_* can discharge the leftover equality — it forces the backtracking cascade we dislike. The plan keeps the adaptor and kills the router: canonicalize the predicate once so routing happens by apply's own unification, and emit a single convert at the root instead of a bespoke one per combinator.

Implementation status — 2026-06-14

Foundation landed and verified green (lake build 535/535, ExtractionAudit passes). The core mechanism is no longer a hypothesis:

  • The extraction claim is confirmed against the audit's exact residue checks. Goal-side simp canonicalization extracts to ↑(_proof.mpr (s_pure 2)) with residue [Subtype.val, Eq.mpr, …] — rejected; the hoisted convert extracts to clean raw Gen (pure 2, (pure 2).pick (pure 5)). This is the reason synth_canon builds a convert rather than rewriting the goal (see §3).
  • Infrastructure in place. Palamedes/SynthNorm.lean registers the @[synth_norm] attribute; CGeneratorSearch.lean seeds it (decide_eq_true_eq, beq_iff_eq, eq_iff_iff), defines synth_canon (one root convert → canonicalize → rflm), and makes normalize_and_apply a first | (synth_canon; direct apply) | (legacy cascade).
  • Additive fast-path live for the unambiguous leaves. s_pure (= e, including decide/== forms) and s_bind (∃) now route by direct apply, skipping the norm_for_* proof. The legacy path remains the fallback, so the change cannot regress coverage; it is one rule, so Aesop branching is unchanged.

The governing constraint, learned the hard way. A first attempt that also direct-applied s_pick regressed ~25 examples. The cause is a design law, not a bug: a rule is only safe to direct-apply if its canonical head has no specialized competitor. Bare apply s_pick can't distinguish a plain ∨ from a case-split, so it steals goals from s_caseNat — that discrimination was hiding inside norm_for_pick's ← Decidable.or_iff_not_imp_left. s_pure/s_bind have no competitor; ∨ genuinely belongs to Phase 3. The same hazard bounds how far @[synth_norm] can be enriched: each new lemma must be checked against a full build for the fast-path stealing from s_elements/fold.

Not yet done. The headline metric — deleting norm_for_pure/norm_for_bind/norm_for_pick — is not reached. The legacy leaf branches still do preprocessing the minimal synth_canon does not yet replicate (Eq.comm for reversed equalities, exists_comm/true_and for binds, unfold_matches/guard/Option.bind for complex predicates). Reaching deletion is the Phase 1 normal-form-parity work below, gated build-by-build — exactly the confluence risk the plan flags.

1. Diagnosis: convert is doing two jobs

Every synthesis goal has the same head: CorrectGen ?P. All the discriminating information lives one level down, in the predicate's outermost structure. But each synthesis rule's conclusion is stated in a specific shape: 

s_pure  : CorrectGen (fun a => a = a')
s_bind  : CorrectGen (fun b => ∃ a, P a ∧ Q a b)
s_pick  : CorrectGen (fun a => P a ∨ Q a)
s_caseNat (h : ∀ {a}, P a n = Q a) ... : CorrectGen Q   -- convert baked in via h

The user's predicate arrives as a concrete Bool function — a match, &&, decide, Option.bind/guard — whose top connective is not syntactically ∨ / = / ∃. To bridge that gap we reach for convert, and there the two jobs get welded together.

The job worth keeping: convert as adaptor

Look at what convert actually is (CorrectGen.lean):

def convert (h : P = Q) (g : CorrectGen P) : CorrectGen Q :=
  Subtype.mk g.val (by simp [h, g.property])
@[extract] theorem convert_val ... : (convert h g).val = g.val := rfl

It is value-transparent (.val is g.val by rfl) and the equality h lives only in the proof field, which is erased at extraction. That single fact is responsible for two properties we genuinely depend on:

  • Extraction stays clean. The combinator discipline — every node built from an s_*/convert combinator with an @[extract] _val rfl-lemma — is what guarantees the synthesized term reduces to raw Subtype.mk; ExtractionAudit.lean enforces exactly that invariant. convert respects it because it is a no-op on the value: the propositional massaging is quarantined where extraction throws it away.
  • Synthesis is complete up to provable equality. convert's ?pf slot can call arbitrary automation, so any predicate we can prove equal to a matched shape is in scope — strictly more than a fixed rewrite system can reach. (In practice today this is bounded by what the bespoke norm_for_X proves, not arbitrary automation; the generality is real but we are currently under-using it.)

The job that hurts: convert as router

  1. Unification can't route the bare goal. So normalize_and_apply (the 99% rule) opens with apply convert ?pf ?arg, making ?arg : CorrectGen ?P with ?P a fresh metavariable. Now apply s_pick always succeeds (it just sets ?P), so routing is no longer decided by apply — it's decided by whether the leftover ?pf : ?P = G can be proved. That is why the rule is a backtracking first | norm_for_pure | norm_for_bind | norm_for_pick cascade.
  2. The leftover equality is propositional, not definitional (it needs eq_iff_iff, ∃-commutation, true_and, Bool ↔ Prop), so each combinator needs its own norm_for_* to rewrite one side into the other's shape. The reconciliation work is duplicated per rule because it is being done after a blind match rather than once, up front.
  3. Indexing can't prune it either (head is always CorrectGen), so the fold path and the case rules re-derive routing by hand: goal_is_not_fold_*, goal_is_or, and the brute-force s_caseNat (by nth_assumption 0/1/2/3) ... enumeration of which subterm is the case index.

Everything brittle is downstream of the router role, and the router role is downstream of one root cause: the predicate is never put into a form where its outermost structure is apparent before we match. Fix that, and convert reverts to being a pure adaptor — used once, in the open, against a known target.

3. The plan: hoist convert, route by apply

Introduce one canonicalizer, synth_canon, backed by a closed simp-attribute set @[synth_norm] with a written normal-form spec. It computes the canonical predicate and exposes its outermost head, each mapping to exactly one rule class: 

-- canonical heads, each mapping to exactly one rule class:
fun a => a = e             →  s_pure
fun a => P a ∨ Q a         →  s_pick     / s_case*
fun b => ∃ a, P a ∧ Q a b  →  s_bind
fun a => <match on data>    →  s_case* / s_unfold (fold path)

Once the head is explicit, routing happens by apply's own unification — reliably, and without depending on discrimination-tree indexing under binders (which is unreliable for CorrectGen (fun a => …)). convert does not disappear; it moves. Instead of one bespoke convert per combinator, with a target that's a fresh mvar and a proof that doubles as the router, we emit one convert at the root against the known canonical target, and then apply the matching rule directly.

Why canonicalization must build the convert — not simp the goal

The obvious implementation, synth_canon = simp only [synth_norm] run on the CorrectGen P goal, breaks extraction, and it breaks it in exactly the way ExtractionAudit.lean is built to catch. Rewriting the goal's type from CorrectGen G to CorrectGen G' is a propositional rewrite, so it inserts an Eq.mpr cast into the value-bearing proof term — and the extract simp set has no lemma to push .val through it. (This is the same class of leakage as the id wrappers we already had to handle with id_eq; Eq.mpr is the harder cousin.)

Confirmed empirically (Lean v4.30.0). Synthesizing CorrectGen (fun n => decide (n = 2) = true) two ways and extracting .val:

-- (A) goal-side: simp only [decide_eq_true_eq]; exact s_pure 2
extracted = ↑(cgenA._proof_1.mpr (s_pure 2))
residue   = [Subtype.val, Eq.mpr, CorrectGen, s_pure]     -- audit REJECTS

-- (B) convert: apply convert ?pf (s_pure 2); case pf => funext n; simp
extracted = pure 2
residue   = []                                            -- clean

The Eq.mpr from the goal rewrite survives and drags Subtype.val and s_pure along with it. convert parks the same equality in _proof_1, which is erased, and convert_val + s_pure_val reduce to pure 2. So synth_canon is a metaprogram that computes G', proves G = G' from the @[synth_norm] set, and emits convert once — keeping the cast in the erased field. This is the mechanical reason the adaptor cannot simply be replaced by a goal normalizer.

What this removes

  • The per-combinator norm_for_* cascade. After the single root convert to canonical form, the goal is literally CorrectGen (fun a => _ ∨ _), so apply s_pick unifies directly and no per-rule equality side-goal is created. The norm_for_pure/norm_for_bind/norm_for_pick trio collapses into the one canonicalizer plus, at most, a residual rflm.
  • The convert-as-router pattern (apply convert ?pf ?arg with a fresh-mvar target whose proof decides routing). The combinator convert stays; what goes is using it to defer rule choice to a backtracking proof search.
  • The goal_is_* routing guards in the common combinators: apply now fails fast on the wrong rule (e.g. fun a => ?P a ∨ ?Q a won't unify with a non-∨ head), so guards are no longer needed to prevent spurious matches.
  • The nth_assumption 0/1/2/3 enumeration in the case rules: in canonical form the scrutinee is explicit, so a small metaprogram picks the case index directly and hands it to s_caseNat — one rule instead of four-per-connective.
  • The duplicated inline simp only exclusion lists: one @[synth_norm] set, defined and tested in one place.

What this does not fix (calibrated expectations)

The fold/unfold path (*_coerce_fold, *_convert_to_accuM, the merge rewrites) is different in kind. Those apply substantive representation-change theorems (coerce_to_fold, fold_accu_Option_*), and which accu lemma applies is itself a backtracking search. Canonicalization can route a predicate into “this is fold-shaped” (subsuming the goal_is_not_fold_* probes) and centralize the simp, but it cannot pick the accu lemma for you. That part stays a guided first | … search, and the library_search calls nested inside it stay a perf/robustness liability until each accu choice can be made deterministic. Note this path is itself convert-shaped — s_elements and the coercions are the adaptor used for an essential representation change, which is further evidence that convert is the right primitive, not a smell. This matches the existing finding that s_unfold + s_caseNat is the part of the system whose complexity is essential.

4. Why I'm confident the core works

  1. The two benefits are preserved by construction. Extraction stays clean because the single root convert keeps the canonicalization cast in the erased proof field (the test above is the proof); completeness up to provable equality stays because the canonical target is still reached via a convert proof, now invoked once and in the open. We are relocating the adaptor, not removing it.
  2. Routing-by-apply is reliable; routing-by-index is not. The plan deliberately leans on unification failure (well-understood, deterministic) rather than discr-tree indexing under lambdas (unreliable), and rather than routing-by-proof (the cascade). So the routing claim doesn't rest on a shaky assumption.
  3. The mvar-assignment already works. s_caseNat's h : ∀ {a}, P a n = Q a closed by rflm is a live, working example of exactly the “assign the higher-order predicate” step we'd reuse. We're not inventing a mechanism, we're feeding it cleaner input.
  4. The canonicalization step already exists in pieces. preprocess (funext + simp [eq_iff_iff]) and the case' pf => unfold_matches; simp […] prefix already do partial normalization successfully — today as the proof side of a convert. We are consolidating and specifying them, and moving the call site to the root, not building from zero.
  5. It degrades gracefully. Where the canonical form doesn't reach a lemma's exact shape, the residual is still discharged by the same convert/rflm we use today. Worst case for an un-improved predicate is status quo, so the change can't regress coverage — only reduce the per-combinator machinery the covered cases need.

5. Phased, testable rollout

1

Specify and build @[synth_norm] + synth_canon

Write the normal-form spec (heads above). Move the scattered simp only lists into one attribute set. Implement synth_canon as a metaprogram that computes the canonical predicate and emits a single convert — not a goal-side simp (see §3: that injects Eq.mpr the audit rejects). Test: #guard_msgs snapshots that each Examples/Simple and Examples/Range predicate normalizes to its expected head, and that ExtractionAudit stays green on the canonicalized terms (the Eq.mpr-residue regression is the one to watch first).

2

Direct-apply the leaf combinators

Rewrite normalize_and_apply so that after synth_canon it does first | apply s_pure | apply s_bind | apply s_pick on the canonical head, with a single rflm fallback for residual defeq. Measure: the norm_for_* branches eliminated and the convert-as-router call sites removed; confirm Examples/Simple, Examples/Range, List/AllTwos/AllTwos.lean still elaborate and ExtractionAudit stays green.

3

Replace case-rule enumeration

Swap the eight goal_is_or; … nth_assumption k rules for one metaprogram that reads the scrutinee from the canonical match and applies s_caseNat/s_caseBool/… once. Test: the case-analysis examples (Nat/Bool/Color) plus a profile run to confirm the smaller rule set doesn't slow Aesop.

4

Fold path: routing only

Let synth_canon tag “fold-shaped” predicates so the goal_is_not_fold_* probes become a single classification, and the coerce_to_fold step keys off it. Leave the accu-lemma first | … search intact — it is the essential-complexity convert-shaped core. Test: every Fold.lean in the corpus, plus scripts/profile.py before/after to watch for synthesis-time regressions.

Success metrics

  • lake build green, ExtractionAudit.lean green (no surviving CorrectGen/Eq.mpr residue).
  • Net reduction in macro count in CGeneratorSearch.lean — target: the norm_for_pure/bind/pick trio gone, the convert-as-router call sites and goal_is_* guards on leaf rules gone, case rules 8 → 1. The convert combinator remains, now called once per goal.
  • scripts/profile.py synthesis time flat or better (smaller rule set, no per-rule proof backtracking).

6. Risks & mitigations

RiskMitigation
Canonicalization reintroduces Eq.mpr residue (implemented as goal-simp instead of as an explicit convert). This is the headline failure mode (§3). Implement synth_canon as a metaprogram that emits convert; gate with the ExtractionAudit snapshot from Phase 1 so any regression to goal-rewriting is caught immediately.
The @[synth_norm] set isn't confluent → canonical form is unstable. Pin it with #guard_msgs normalization snapshots in Phase 1; the spec is the contract.
A predicate normalizes to a head no rule expects. The residual is discharged by the same convert/rflm we use today, so coverage is preserved; the new direct-apply path is strictly additive.
Fold path resists routing. Scoped out by design (Phase 4 is routing-only); no claim that the accu search is replaced.
Mistaken for the dead Canonical experiment. This stays entirely in Prop and in the existing s_*/CorrectGen architecture — no Desc, no reflect, no external solver, no new subtype. convert is retained as the adaptor.
Scope note: this plan is deliberately incremental and reversible per phase. The biggest, most reliable win (Phases 1–2) lands first and de-risks the rest. convert is treated as the load-bearing primitive it is — the cleanliness of extraction and completeness up to provable equality both depend on its erased-proof, value-transparent shape — so the work is to hoist and unify its use, not to remove it. The fold machinery is essential complexity, not something to canonicalize away.
